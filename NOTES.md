# Заметки по проекту

## Правило: «Окну взаимодействия» отдаём любые данные, которые оно запросит

Окно взаимодействия — наш же сервис, вынесенный в отдельный проект. Если оно
просит данные по API — делаем эндпоинт и отдаём, не споря и не урезая:
ученики, брони, платежи, анкеты, сотрудники, смены, статусы CRM.

Как это делается (уже работает по этой схеме):
- запрос от окна к нам — действие в нужной функции + проверка `X-Service-Key`
  (секрет `INTERACTION_SERVICE_KEY`), сессия сотрудника не требуется;
  образцы: `staff-auth` → `verify_session`, `service_assignees`;
- запрос от нас к окну — POST-хук на
  `https://functions.poehali.dev/67e8d62d-902a-4e5e-9862-d18395a730b1?action=<...>`
  с тем же ключом; образцы: `admin-shifts` (`shift-hook`),
  `questionnaire/form_hook.py` (`form-hook`),
  `get-payment-leads/payment_hook.py` (`payment-hook`),
  `slot-bookings` (`booking-hook`);
- на каждый хук — подстраховка `action=feed&status=new`, чтобы окно могло
  забрать пропущенное само.

Единственные границы: значения секретов в браузер не отдаём (проверка только
на бэкенде) и открытых эндпоинтов без ключа для персональных данных не делаем.

## Отложено: Единое окно коммуникации с клиентами

Вернуться к этой задаче позже. Договорённости с заказчиком:

**Цель:** собрать всё общение с клиентами (Max, Telegram, звонки) в единую ленту
«Коммуникация» у каждого ученика, с удобной передачей между сотрудниками
(диагност / админ / руководитель).

**Вводные от заказчика:**
- Max подключён через Wappi, всё на одном номере телефона.
- Телефония: пока НЕ звоним по API, записей звонков нет (расшифровка — только когда
  появится IP-телефония с записью; Yandex SpeechKit уже доступен в проекте).
- Единую ленту хранить у нас, в разделе «Коммуникация»; в AlfaCRM (S20) — только
  короткие пометки (у S20 нет API-метода писать переписку в карточку).
- Вход сотрудников: личный вход у каждого. ЛОГИН = НОМЕР ТЕЛЕФОНА.
- Регистрация: САМОСТОЯТЕЛЬНАЯ (сотрудник регистрируется сам → руководитель
  подтверждает/активирует аккаунт). До подтверждения — доступа нет.
- Охват: ВСЕ сотрудники, ВКЛЮЧАЯ ПЕДАГОГОВ. Роли: педагог, диагност, администратор,
  руководитель. Масштаб 15–40 человек, состав меняется → таблица сотрудников в БД
  + раздел управления, ручной хардкод-список ADMINS больше НЕ подходит.
- Первый приоритет заказчика: **передача общения между сотрудниками**.

**РЕШЕНО начать с ЭТАПА 0 (личные кабинеты сотрудников) ДО окна коммуникации.**
- Переход: старый общий пароль 426874 РАБОТАЕТ ПАРАЛЛЕЛЬНО с новым личным входом
  (пока все не зарегистрируются). НЕ отключаем сразу.
- Роль при регистрации: сотрудник ВЫБИРАЕТ САМ.
- ИЗМЕНЕНО: руководитель НЕ подтверждает регистрацию вручную. Вместо этого при
  регистрации идёт АВТОПРОВЕРКА по S20 (раздел сотрудников /v2api/1/employee/index):
  совпадение по ТЕЛЕФОНУ ИЛИ ФИО → сразу status=active; нет совпадения → отказ
  "Нет совпадений в CRM". Реализовано в backend/staff-auth (match_in_s20, сканирует
  все строковые поля employee). Раздел «Сотрудники» у руководителя оставлен как
  инструмент (роли/блокировка), но подтверждение больше не требуется.
- В staff-auth есть временный debug-эндпоинт ?action=debug_employees (посмотреть
  поля S20 employee) — УБРАТЬ после проверки схемы.
